# CLAUDE.md — AI assistant guide

This file is the canonical source of truth for AI tools (Claude, Cursor,
Copilot, Windsurf, etc.) working in this repo. The brief for this assessment
explicitly asks for these files to be checked in — they describe **how** the
work was built, not just **what** was built.

## Project at a glance

- **Assignment:** Cobra Studio backend technical assessment.
- **Scenario:** Option E — Pet Adoption Board.
- **Stack:** NestJS 11 · TypeScript 5 (`strict: true`) · PostgreSQL 16 ·
  Sequelize v6 + `sequelize-typescript` v2 · `@nestjs/jwt` + `passport-jwt` ·
  `class-validator` · Jest. Optional Next.js frontend in `web/`.
- **Layout:** `api/` (NestJS), `web/` (frontend), `plan.md` (architecture
  decisions), `docker-compose.yml` (Postgres only).

The full architecture and decisions live in `plan.md`. **Read `plan.md`
before making structural changes.**

## How to work in this repo

### Code rules

1. **TypeScript strict mode is non-negotiable.** `tsconfig.json` enables
   `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`,
   `noImplicitOverride`, `noUnusedLocals`, `noUnusedParameters`. Don't relax
   any of these. If a type cast feels necessary, prefer narrowing or a typed
   helper over `as` / `any`.
2. **One concern per module.** New domain features go in
   `api/src/modules/<feature>/` with a controller, service, model, and DTOs.
3. **Validation at the boundary.** Every request body and query is a class
   decorated with `class-validator`. The global `ValidationPipe` is
   configured with `whitelist: true`, `forbidNonWhitelisted: true`,
   `transform: true`. Don't bypass it.
4. **Authorization belongs in services and guards, not controllers.**
   Controllers wire HTTP; services enforce who-can-do-what. The `RolesGuard`
   covers role-based gates. Owner-scoped reads belong in service queries
   (filter by `user_id`), not in controller code.
5. **Errors are structured.** Throw `HttpException` subclasses with a clear
   message; let `AllExceptionsFilter` shape the response envelope. Don't
   write raw `res.status(...).json(...)`.
6. **No `console.log` in production paths and no commented-out code.** Use
   the Nest logger (`Logger` from `@nestjs/common`) when something needs to
   surface, and delete dead code rather than commenting it.
7. **Transactions for multi-row state changes.** The application
   approve-cascade is the canonical example — pet update + sibling rejects
   must happen inside one Sequelize transaction.

### Files an AI tool should *not* touch without a clear reason

- `api/package-lock.json` — committed; let `npm install` manage it.
- `api/dist/`, `api/coverage/`, `api/node_modules/` — gitignored, never
  edited.
- Migrations (when added) — they are append-only.
- The author's git config (`riquelmy.melara@tecniastudio.com`) — don't
  override.

### Commit conventions

- Commits are made by the author; they should never include AI co-author
  trailers (`Co-Authored-By: Claude` etc.) or "generated by" footers. Just
  describe the change.
- Subject line: imperative, ≤ 72 chars.
- Body: short bullets explaining the *why* if it isn't obvious from the
  diff. Reference business rules from `plan.md` when relevant.
- Commit early and often. Each module landing is a commit. Each tightening
  pass is a commit.

### Testing

- Unit tests live next to the file as `*.spec.ts`; the heavyweight ones
  for `ApplicationsService` are the most important — every business rule
  in `plan.md` should have a test.
- E2E tests live in `api/test/` and use `supertest` with the global pipes /
  filters wired the same way as `main.ts`.
- Don't chase coverage numbers. Test the rules, not the framework.

### When in doubt

- Re-read `plan.md` for the chosen decision and its rationale.
- Prefer the simpler option that fits the brief; this is a 24-hour
  assessment, not a production codebase. Mark deliberate omissions as
  "Out of scope" in the README rather than half-implementing them.

## Useful commands

```bash
# Start Postgres
docker compose up -d

# Backend dev
cd api
cp .env.example .env  # first time
npm install
npm run start:dev

# Other backend commands
npm run build        # tsc + nest build
npm run lint
npm run test         # unit
npm run test:e2e
npm run seed         # populate DB with sample data
```
